**TL;DR**: OpenSearch 3.7 では、`_source` の代わりに `docvalue_fields` を使ってベクトルを取得できるようになりました。列指向ストアから 1 回のシークで直接読み出すため、k=1000 でエンドツーエンドのレイテンシが 5.5 倍、サーバー側の処理が 14.7 倍高速になります。再インデックスは不要で、既存のすべてのインデックスとベクトル型で動作します。Base64 バイナリ形式を使えばレスポンスのペイロードが 70% 小さくなります。大きな k を扱う RAG パイプラインやリランキングなど、レスポンスにベクトルそのものを返す必要があるワークフローに最適です。
:::

ベクトル検索は、最近傍を見つけて終わりではありません。実際のアプリケーションの多くは、ベクトルそのものをレスポンスに返す必要があります。たとえば検索拡張生成（RAG）パイプラインでは、後続の大規模言語モデル（LLM）呼び出しに渡すコンテキストの埋め込みを取得します。リランキングシステムはクロスエンコーダのスコアを計算し、クライアント側の後処理では多様性やビジネスルールに基づくフィルタリングを適用します。k が大きくなる（k=100、k=500、さらには k=1000）につれて、これらのベクトルを返すコストがクエリ全体のレイテンシを支配し始めます。

OpenSearch 3.7 では、列指向で格納されたベクトルを `docvalue_fields` から取得する最適化された方法が導入されました。これにより、コストの高い `_source` によるベクトル再構築の経路を回避できます。この機能は再インデックスを必要とせず、古いインデックスを含むすべての既存インデックスで動作し、あらゆるベクトルのデータ型に対応します。その結果、エンドツーエンドのレイテンシが **5.5 倍**、サーバー側の処理が **14.7 倍** 高速になります（いずれも k=1000 の場合）。

## 従来の `_source` による取得経路

なぜこれが重要なのかを理解するために、従来の `_source` 経路で検索結果にベクトルを要求したときに何が起きるかを見てみましょう。

OpenSearch 3.0 以降、ベクトルは `.fdt`（stored fields）ファイルには格納されなくなりました。代わりに `.vec` ファイルに列指向形式で格納されます。これはベクトルへの逐次アクセスに最適化された構造です。この変更は [ベクトルの派生ソース（derived source for vectors）](https://opensearch.org/blog/Do-More-with-Less-Save-Up-to-3x-on-Storage-with-Derived-Vector-Source/) の一部として導入され、ストレージコストを最大 3 分の 1 に削減しました。

しかし `_source` を使ってベクトルを要求すると、OpenSearch は依然として次のような複数ステップの再構築処理をたどります。

1. ディスク上の `.fdt` ファイルから、圧縮された `_source`（ベクトルは含まない）を **読み込む**。
2. stored field のデータを **展開する**。
3. 生バイト列をドキュメントのマップに **デシリアライズする**。
4. `.vec` ファイルからベクトルを **読み込み**、デシリアライズ済みのドキュメントの正しいフィールドパスに **注入する**。
5. レスポンスとして返すために、ドキュメント全体を JSON バイト列へ **再シリアライズする**。

これらのステップはすべて *ドキュメントごと* に実行されます。768 次元のベクトルで k=1000 の場合、およそ 8 MB 分のレスポンスデータを、ドキュメントごとに読み込み・展開・デシリアライズ・注入・再シリアライズすることになります。

私たちのベンチマークでは、この再構築のオーバーヘッドだけで、k が大きいときにクエリあたり数十ミリ秒に達することがあります。この時間は、すぐにアクセスできる列指向形式にすでに存在するデータを組み立て直すためだけに費やされています。ベクトルは逐次アクセスに最適化された列指向構造としてそこにあるのに、`_source` 経由で読むのは無駄に遠回りなのです。

## 列指向ストアから直接ベクトルを取得する

doc values を使ったベクトル取得では、レスポンス内でベクトルと非ベクトルフィールドを分離します。前節で説明した `_source` の再構築パイプラインを経由する代わりに、OpenSearch は `_source` には手を加えず、列指向ストアから **ドキュメントごとに 1 回のシーク** でベクトルを直接読み出します。取得したベクトルは、レスポンス内の別の `fields` キーに返されます。

非ベクトルフィールド（タイトル、テキスト、メタデータ）は従来どおり `_source` から提供されます。ベクトルを `_source` 経路から完全に切り離すことで、元のドキュメントソースを変更したり再処理したりすることなく、再構築パイプラインで最もコストの高いステップであるベクトルの注入を排除できます。

2 つの取得経路を比較すると次のようになります。

```
doc values 経路（ドキュメントごと）:

  非ベクトルフィールド:  .fdt (ディスク) ──► 展開 ──► デシリアライズ ──► レスポンス
  ベクトルフィールド:    列指向ストア ──► ベクトルのバイト列 ──► エンコード ──► レスポンス

  _source へのベクトル注入なし。ドキュメント全体の再シリアライズなし。
```

### doc values による取得の流れ

`knn_vector` フィールド型が、検索リクエストで `docvalue_fields` パラメータをサポートするようになりました。`docvalue_fields` でベクトルフィールドを要求すると、OpenSearch は次の処理を行います。

1. 列指向のベクトルストアの中で、ドキュメントの序数（オーディナル）を検索する。
2. 生のベクトルのバイト列を、1 回の逐次読み出しで直接読み込む。
3. ベクトルを要求された形式（Base64 バイナリまたは JSON 配列）にエンコードする。

このベクトル取得は `_source` から完全に独立しています。ベクトルのデータのために stored fields ファイルにアクセスすることはありません。OpenSearch はベクトルについて、展開・注入・再シリアライズのパイプラインを完全にスキップします。

### 出力形式

doc values を使ったベクトル取得は、以下の出力形式をサポートします。

| 形式 | 説明 | レスポンスサイズ（768 次元、k=1000） | 適した用途 |
|---|---|---|---|
| `binary`（デフォルト） | Base64 エンコードされたリトルエンディアンの float バイト列 | 約 2.5 MB | プログラムから利用するクライアント、パフォーマンスが重要な経路 |
| `array` | JSON の数値配列 | 約 6 MB | デバッグ、人による確認、シンプルなクライアント |

デフォルトが binary 形式なのは、高次元ベクトルにおいて JSON 配列よりレスポンスがおよそ 60% 小さくなるためです。これにより、サーバー側でシリアライズするデータ量、ネットワークで転送するデータ量、クライアント側でパースするデータ量が減ります。

### 互換性

doc values を使ったベクトル取得は、以下と組み合わせて動作します。

- **すべての k-NN エンジン**: Lucene、Faiss、NMSLIB
- **すべてのベクトルのデータ型**: `float`、`byte`、`binary`
- **すべての圧縮レベル**: 量子化の設定に制限はありません
- **既存のインデックス**: 再インデックスは不要で、過去のどのバージョンの OpenSearch で作成したインデックスでも動作します

## doc values を使ったベクトル取得の使い方

以下の例では、`docvalue_fields` を使ってベクトルを取得するさまざまな方法を示します。

### 基本的な使い方（binary 形式、デフォルト）

```json
POST /my_index/_search
{
  "query": {
    "knn": {
      "my_vector": {
        "vector": [0.1, 0.2, 0.3, ...],
        "k": 100
      }
    }
  },
  "docvalue_fields": ["my_vector"],
  "_source": false
}
```

### 形式を明示的に指定する

```json
POST /my_index/_search
{
  "query": {
    "knn": {
      "my_vector": {
        "vector": [0.1, 0.2, 0.3, ...],
        "k": 100
      }
    }
  },
  "docvalue_fields": [
    {"field": "my_vector", "format": "binary"}
  ],
  "_source": false
}
```

### `_source` からベクトルを除外して doc values を使う

ベクトルフィールドを `_source` から除外し、`docvalue_fields` で取得することを推奨します。こうすると、ベクトル再構築のオーバーヘッドなしに、`_source` からドキュメントのメタデータ（タイトル、テキスト、タイムスタンプ）をそのまま取得しつつ、ベクトルは列指向ストアから直接得られます。

```json
POST /my_index/_search
{
  "query": {
    "knn": {
      "my_vector": {
        "vector": [0.1, 0.2, 0.3, ...],
        "k": 100
      }
    }
  },
  "docvalue_fields": [{"field": "my_vector", "format": "binary"}],
  "_source": {
    "excludes": ["my_vector"]
  }
}
```

### 最大限のパフォーマンスのためにベクトルだけを取得する

（リランキングパイプラインなどで）ベクトルとドキュメント ID だけが必要な場合は、`_source` と stored field のオーバーヘッドをすべて排除できます。次のリクエストは、ドキュメント ID とベクトルのバイト列だけを返します。

```json
POST /my_index/_search
{
  "query": {
    "knn": {
      "my_vector": {
        "vector": [0.1, 0.2, 0.3, ...],
        "k": 1000
      }
    }
  },
  "stored_fields": "_none_",
  "docvalue_fields": ["_id", {"field": "my_vector", "format": "binary"}],
  "_source": false
}
```

### レスポンスの形式

**binary 形式:**

```json
{
  "hits": {
    "hits": [
      {
        "_id": "doc_1",
        "_score": 0.95,
        "fields": {
          "my_vector": ["AACAPwAAAEAAAEBAAACAQA=="]
        }
      }
    ]
  }
}
```

このレスポンスでは、Base64 文字列をデコードするとリトルエンディアン順の生の float バイト列になります。ほとんどのクライアントライブラリ（Python の `struct`、Java の `ByteBuffer`、NumPy の `frombuffer`）はこれを直接デコードできます。

**array 形式:**

```json
{
  "hits": {
    "hits": [
      {
        "_id": "doc_1",
        "_score": 0.95,
        "fields": {
          "my_vector": [[1.0, 2.0, 3.0, 4.0]]
        }
      }
    ]
  }
}
```

## ベンチマーク結果

実際の改善幅を測定するため、doc values を使ったベクトル取得を従来の `_source` による取得と比較しました。構成を変えて計測しています。

### 構成

ベンチマークでは以下の構成を使用しました。

- **データセット**: Cohere-1M（1,000,000 ベクトル、768 次元）
- **クラスタ**: r8id.4xlarge × 3（各 16 vCPU、128 GB RAM）
- **インデックス構成**: 1 シャード、2 レプリカ、Faiss による HNSW（Hierarchical Navigable Small World）、`ef_construction`=128、`m`=16、`ef_search`=32
- シャードあたり 1 セグメントに **force merge** 済み
- **クエリ**: 10,000 クエリ、シングルスレッド、ノードへの直接接続
- **クライアント**: コネクションプーリングを有効にした OpenSearch Python クライアント（`opensearch-py`）

### k=1000 の結果

k=1000 では `_source` のオーバーヘッドが支配的になるため、改善は劇的です。以下の図に示します。

![k=1000 におけるレイテンシの比較](/images/retrieve-vectors-5x-faster-with-docvalue_fields/acb0bb61bcc3.png)
*k=1000 におけるレイテンシの比較*

以下の表に k=1000 でのレイテンシの比較を示します。

| 方式 | E2E p50 | E2E p90 | サーバー側（took）p50 | 改善率（E2E p50） | 改善率（サーバー側 p50） |
|---|---|---|---|---|---|
| `_source`（ベースライン） | 107.2 ms | 133.0 ms | 44.0 ms | — | — |
| doc values（binary） | 19.3 ms | 31.9 ms | 3.0 ms | **5.5 倍** | **14.7 倍** |

サーバー側の改善: **44 ms → 3 ms（14.7 倍高速）**

`_source` のオーバーヘッド（展開、デシリアライズ、ベクトルの注入、再シリアライズ）がすべて排除されます。残る 3 ms は k-NN のグラフ探索そのものです。

### k=100 の結果

k=100 では、固定的なコスト（k-NN 探索、ネットワークのラウンドトリップ時間）が全体のレイテンシに占める割合が大きくなるため、改善幅は小さくなります。以下の図に示します。

![k=100 におけるレイテンシの比較](/images/retrieve-vectors-5x-faster-with-docvalue_fields/ffcc70c9641c.png)
*k=100 におけるレイテンシの比較*

以下の表に k=100 でのレイテンシの比較を示します。

| 方式 | E2E p50 | E2E p90 | サーバー側（took）p50 | 改善率（E2E p50） |
|---|---|---|---|---|
| `_source`（ベースライン） | 16.5 ms | 17.4 ms | 8.0 ms | — |
| doc values（binary） | 6.5 ms | 7.3 ms | 3.0 ms | **2.5 倍** |

k が中程度であっても、意味のあるレイテンシ削減が得られます。特にサーバーレベルでは、stored field の読み込みが 8 ms から 3 ms に下がります。

### CBOR トランスポート

CBOR（Concise Binary Object Representation）や Smile といったバイナリのトランスポートプロトコルを使うアプリケーションでは、改善はさらに顕著になります。これらの形式では `_source` 経路が特に高コストだからです。以下の表に示します。

| 方式 | トランスポート | E2E p50 | `_source` に対する改善率（CBOR） |
|---|---|---|---|
| `_source`（ベースライン） | CBOR | 92.3 ms | — |
| doc values（binary） | CBOR | 17.8 ms | **5.2 倍** |

### コンポーネント別のレイテンシの内訳

k=1000 で改善がこれほど大きい理由を理解するために、コストの内訳を見てみましょう。以下の図に示します。

![k=1000 におけるコストの内訳](/images/retrieve-vectors-5x-faster-with-docvalue_fields/991e30f9de50.png)
*k=1000 におけるコストの内訳*

以下の表に、各コンポーネントで費やされる時間を示します。

| コンポーネント | `_source` 経路 | doc values 経路 | k に比例するか |
|---|---|---|---|
| k-NN グラフ探索 | 約 2〜3 ms | 約 2〜3 ms | しない |
| stored field の読み込み | 約 40 ms | 0 ms | する（線形） |
| doc value の読み込み | 0 ms | 1 ms 未満 | ほぼ無視できる |
| レスポンスの転送 | 約 15 ms | 約 13 ms | する（線形） |
| クライアントの JSON パース | 約 46 ms | 約 3.7 ms | する（線形） |
| **合計 E2E** | **約 107 ms** | **約 19 ms** | |

レイテンシ削減の大部分は、stored field の読み込み（40 ms）と、クライアント側の JSON パース（46 ms に対し、コンパクトな Base64 エンコードでは 3.7 ms）が占めています。

以下の図に、取得方式ごとのレスポンスのペイロードサイズを比較します。

![レスポンスのペイロードの比較](/images/retrieve-vectors-5x-faster-with-docvalue_fields/2a0510e2d7d6.png)
*レスポンスのペイロードの比較*

以下の表に、各方式のレスポンスサイズを示します。

| 方式 | レスポンスサイズ（k=1000、768 次元） |
|---|---|
| `_source`（ドキュメント全体） | 約 8 MB |
| doc values（JSON 配列） | 約 6 MB |
| doc values（binary / Base64） | 約 2.5 MB |

binary エンコードは、`_source` によるドキュメント全体の取得と比べてレスポンスのペイロードを **70% 削減** します。

## doc values を使ったベクトル取得が有効な場面

doc values を使ったベクトル取得が最も効果を発揮するのは、次のような場合です。

- **k が大きい**（k=100 以上）: `_source` のオーバーヘッドは、返すドキュメント数に対して線形に増加します。
- **RAG パイプライン**: LLM に渡すコンテキストの埋め込みを取得する場面。ベクトルは必要だがドキュメント全体のソースは不要な場合です。
- **リランキングのワークフロー**: クライアント側やクロスエンコーダによる再スコアリングのためにベクトルを取得する場面。

レスポンスにベクトルが不要なクエリ（ユーザー向け検索ではこちらが一般的です）では、これまでどおり `_source.excludes` でベクトルフィールドを除外してください。ベクトルのバイト列がまったく転送されないため、これが最速の選択肢であることに変わりはありません。

## 今後の予定: OpenSearch 3.8 における Base64 バイナリでのベクトル取り込み

doc values を使ったベクトル取得は、取得側のパフォーマンス問題を解決します。では、取り込み（ingestion）側はどうでしょうか。

現在、ベクトルは JSON の数値配列として OpenSearch に送られます。768 次元の float ベクトルは 768 個の数値からなる JSON 配列となり、ベクトルあたりネットワーク上で約 6 KB を消費します。[OpenSearch 3.8](https://github.com/opensearch-project/k-NN/issues/3322) では **Base64 バイナリによるベクトルの取り込み** が導入され、クライアントは JSON 配列の代わりにコンパクトな Base64 エンコードのバイト文字列としてベクトルを送れるようになります。

doc values を使ったベクトル取得と組み合わせることで、完全な **バイナリの往復** が実現します。ベクトルを Base64 で取り込み、効率的に格納し、Base64 で取得する。リクエストのライフサイクルのどの段階でも JSON の数値配列をパースする必要がなくなります。

## まとめ

OpenSearch 3.0 では [ベクトルの派生ソース（derived source for vectors）](https://opensearch.org/blog/Do-More-with-Less-Save-Up-to-3x-on-Storage-with-Derived-Vector-Source/) が導入され、ベクトルを `_source` から取り除くことでストレージコストを最大 3 分の 1 に削減しました。OpenSearch 3.7 では、doc values を使ったベクトル取得により、ベクトルを読む際に最もコストの高い部分、すなわち `_source` の展開と再シリアライズのパイプラインを排除します。列指向で格納された形式からベクトルを直接読み出し、コンパクトな Base64 文字列としてエンコードすることで、OpenSearch はクエリパラメータを 1 つ変えるだけで、k=1000 において **エンドツーエンドで 5.5 倍高速** なレイテンシを実現します。

- [Retrieving vector fields using docvalue_fields](https://docs.opensearch.org/search-plugins/searching-data/retrieve-specific-fields/) - 特定のフィールドを取得するためのガイド
