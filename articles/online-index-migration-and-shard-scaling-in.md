**TL;DR:** AOSC (Automatic Online Schema Change) プラグインを使うと、稼働中の OpenSearch インデックスを、マッピング・設定・シャード数が異なる新しいターゲットへ、同じクラスタ内で移行できます。既存ドキュメントをバックフィルし、コピー中に到着した書き込みをリプレイし、短時間の書き込みブロックのあとにエイリアスを切り替えます。アプリケーション側は単純なリトライロジックさえあれば済みます。シャード数の変更は、同数のままにするか 2 のべき乗倍に増やす場合であれば安全に行えます。それ以外のレイアウトには注意点があります。AOSC はオープンソース (Apache 2.0) で、Atlassian Labs が開発し、GitHub で公開されています。

OpenSearch を本番環境で長く運用していれば、いずれ OpenSearch がインプレースでは変更を許さない項目、たとえばフィールドの型、アナライザ、ルーティングレイアウト、プライマリシャード数のいずれかを変更したくなる時が来ます。1 年前に設計したマッピングがもはやデータに合わなくなっていたり、30 GB では快適だったシャードが 100 GB では窮屈になっていたりします。

定石は、目的の形の新しいインデックスを作ってデータをコピーすることです。ここまではよく知られています。難しいのは、コピーしている間に稼働中のインデックスで起こることすべてです。ひっきりなしに到着する書き込み、失うわけにはいかない削除、そしてアプリケーションがデータを取りこぼさずに新しいインデックスへ接続を切り替えなければならない瞬間。

本記事では、このワークフローを扱うオープンソースの OpenSearch プラグイン、Automatic Online Schema Change (AOSC) を紹介します。AOSC は、稼働中のインデックスを、事前に作成しておいたターゲットインデックスへ移行します。マッピング・設定・シャード数・ドキュメント形状が異なっていてもかまいません。移行のほとんどの期間、ソースは書き込みを受け付け続けます。既存ドキュメントをバックフィルし、ソースのオペレーション履歴をリプレイしてコピー中の書き込みを失わないようにし、ソースに短時間の明示的な書き込みブロックをかけたうえでエイリアスを切り替えます。

AOSC は無停止のツールではなく、すべての移行に合うわけでもありません。本記事では AOSC が対象とする問題、その仕組み、シャード数を安全にスケールする方法、そして境界がどこにあるかを扱います。自分のワークロードに合うかどうかを判断できるようにするためです。

## 現状のツールで稼働中のインデックスを作り直す

OpenSearch には、データを移動したり作り直したりする手段がいくつか用意されています。それぞれ特定の状況にはよく合いますが、ソースインデックスが継続的な書き込み負荷にさらされているとどこかに穴が空きます。

- **[`_reindex`](https://docs.opensearch.org/latest/im-plugin/reindex-data/)** は、ソースのある時点のスナップショットを新しいインデックスへコピーします。ソースを静止できる場合や、コピー中に到着する書き込みを整合させる別経路をすでに持っている場合には、そこそこ妥当な選択肢です。書き込みが多いインデックスでは、その整合こそが問題の中核です。`_reindex` は開始後に着信する書き込みを追跡もリプレイもしません。
- **[`_split`](https://docs.opensearch.org/latest/api-reference/index-apis/split/)** はシャード数を増やせますが、整数倍への拡張のみ、`read-only` にマークしたインデックスに対してのみ、かつインデックスが十分な `routing shards` を持つように作成されている場合に限られます。ドキュメントの作り直しやマッピングの変更はできません。
- **[`_shrink`](https://docs.opensearch.org/latest/api-reference/index-apis/shrink-index/)** は独自の前提条件のもとでシャード数を減らせますが、同じくドキュメントには手を加えません。
- **手組みのパイプライン** (`_reindex` を実行し、そのあと変更を追随し、切り替える) は完全な制御を与えてくれますが、バックフィル・書き込みリプレイ・検証・リトライ挙動・ロールバックを自分で設計するコストと引き換えです。そのいずれも、微妙な正しさのバグを埋め込む余地があります。

共通しているのは、ネイティブのプリミティブがソースの書き込み受付停止を要求するか、整合の問題を自分で解けと押し付けてくるかのどちらかだということです。本番の書き込み経路の中心にあるインデックスでは、どちらも心地よくはありません。

![手組みの経路と AOSC の比較図](/images/online-index-migration-and-shard-scaling-in/28ea29a71049.png)
*手組みの経路 (左) では、コピー・二重書き込み・整合・切り替えのロジックをすべてのアプリケーションに埋め込みます。AOSC (右) はアプリケーションを 1 つのエイリアスと通信させたまま、移行処理をクラスタ側へ持ち込みます。*

## AOSC の役割

AOSC は「稼働中のインデックスをコピーして切り替える」ワークフローを 1 つのプラグインにまとめたものです。スコープは、正しく動作させられるケースに意図的に絞られています。

- 移行は単一クラスタ内で行われる (ソースとターゲットが同じ OpenSearch クラスタに存在する)。
- ターゲットインデックスはすでに存在し、目的のマッピング・設定・シャード数で自分で作成しておく。
- アプリケーションは [エイリアス](https://docs.opensearch.org/latest/im-plugin/index-alias/) を介して書き込むため、AOSC は切り替え時にそのエイリアスをソースからターゲットへ付け替えられる。
- アプリケーションは、短い切り替えウィンドウの間に拒否された書き込みをリトライする。

これらの条件のもとで、ソースインデックスに対する 1 回の API 呼び出しから移行を開始します。事前に作成したターゲットと、付け替えたいエイリアスを指定します。任意で [Painless スクリプト](https://docs.opensearch.org/latest/vector-search/vector-search-techniques/painless-functions/) を渡して、移行の途中でドキュメントを作り直すこともできます。このスクリプトはバックフィルとリプレイの両方で動くので、移行の実行中に書き込まれたドキュメントは、最初にコピーされたものと同じ方法で変換されます。以下の例は不要になったフィールドを削除します。

```bash
curl -X POST 'http://localhost:9200/_plugins/_aosc/my-index-v1/_start' \
  -H 'Content-Type: application/json' \
  -d '{
    "target_index": "my-index-v2",
    "alias": "my-index",
    "transform_script": {
      "type": "inline",
      "source": "ctx._source.remove(\"legacy_field\")"
    }
  }'
```

そこから先は AOSC が移行を完了まで進めます。進捗はステータス API を通じて最後まで公開されます。移行ごとのオプションで、切り替え前にシャードがどれだけ遅れていてよいか、ドキュメント数をどの厳しさで検証するかを調整できます。

## 移行はどう進むか

AOSC はオーケストレーションとデータ移動を分離します。コーディネーターは cluster-manager ノード上で動作し、移行を各フェーズへ進めます。シャードワーカーはソースのプライマリシャードを保持するデータノード上で動作し、データのすぐそばで実際の読み書きを行います。移行が実行中の間、そのフェーズは cluster state に保存されます。`.aosc-migrations` システムインデックスは、履歴としての移行レコードを保持します。

![AOSC のアーキテクチャ図](/images/online-index-migration-and-shard-scaling-in/64f0ef8e53a7.png)
*オーケストレーションは cluster-manager ノードで動きます。データ移動の処理はデータノード上、シャードのそばで動きます。この 2 つは cluster state (コーディネーターからワーカーへ) と transport action (ワーカーからコーディネーターへ) を通じて協調します。*

移行が正常に完了する場合は、以下のフェーズを通過します。

1. **Validate (検証)。** ソース・ターゲット・エイリアスが存在し整合していること、プラグインがすべてのノードに同じバージョンでインストールされていること、ルーティングトポロジが AOSC の扱える形になっていること (詳細は後述) を確認します。AOSC はターゲットを作成しません。その形を正確に整えるのはユーザーの役目です。
2. **Prepare the target (ターゲットの準備)。** レプリカを 0 にし refresh を無効化するなど、コピー向けの一時設定を適用してバックフィルを高速に走らせます。これらの設定は切り替え前に元に戻します。
3. **Backfill (バックフィル)。** 各シャードワーカーがソースの既存ドキュメントを読み、ターゲットへインデックスします。変換スクリプトが渡されていればそれを適用します。読み取りは retention lease でアンカーされ、ワーカーが必要とするオペレーション履歴が背後で刈り取られないようにします。
4. **Replay (リプレイ)。** バックフィル後、ワーカーはソースシャードのオペレーション履歴を読み、コピー中に到着した書き込みと削除を適用します。これにより、トラフィックを受け続けているソースにターゲットが追随します。リプレイは、すべてのソースプライマリシャードが切り替え可能なほどソースの現在位置に近づくまで続きます。遅いシャードやホットなシャードがあれば、時期尚早な切り替えを強行するのではなく、移行をこのフェーズに留めます。
5. **Cut over (切り替え)。** AOSC はソースに書き込みブロックをかけ、ワーカーに最後のオペレーションをリプレイさせ、ソースとターゲットのドキュメント数が指定した許容範囲内で一致するかを検証し、エイリアスをソースからターゲットへ付け替えます。
6. **Complete (完了)。** エイリアスはターゲットを指すようになります。デフォルトでは、エイリアス移動後に旧ソースが黙って書き込みを受け付けないよう、旧ソースには書き込みブロックが残ります。自動でブロックを解除する動作にオプトインすることもできます。

![AOSC の移行フローチャート](/images/online-index-migration-and-shard-scaling-in/11e7e9af4b82.png)
*移行の全体像を 1 枚で示します。シャード単位のバックフィルとリプレイはソースを稼働させたまま実行し、そのあとの短い書き込みブロック区間で最終リプレイ、件数チェック、エイリアス付け替えを行います。*

ドキュメントに用意されているインタラクティブなウォークスルーは、これらのフェーズを、プラグインが実際に報告するステータスフィールドと対応付けてアニメーション表示します。初めて実行する前に頭の中でモデルを組み立てるのに役立ちます。

## 切り替えウィンドウ

切り替えは、アプリケーションが実際に感じ取る唯一の中断です。切り替えの間は、ワーカーが最後のオペレーションをリプレイしエイリアスが付け替わるまでの間、ソースへの書き込みが拒否されます。このウィンドウは意図的に設けられています。トラフィックが移る前に、ターゲットが追いついたことを AOSC が確認するためのものです。ゴールは、ウィンドウが存在しないふりをすることではなく、短く保つことです。

このウィンドウの長さは、インデックスサイズ・シャード数・書き込み負荷・検証コスト・cluster-manager の応答性に依存するので、単一の数字を信じるのではなく自分のワークロードで計測してください。AOSC はウィンドウを短く保つように作られています。既知の制限に、実運用で観測される範囲が記されています。ユーザー側の役目はリトライです。ブロックがかかっている間に拒否された書き込みをアプリケーションがリトライすることで、エンドユーザーからはウィンドウが見えなくなります。

## 移行のモニタリング

すべての移行はステータスエンドポイントから観測できるので、進捗について推測する必要はありません。

```bash
curl -s 'http://localhost:9200/_plugins/_aosc/my-index-v1/_status' | jq '.phase'
```

レスポンス全体には、コーディネーターのフェーズ、バックフィルとリプレイのシャード単位の進捗、そして切り替えが完了すればソースとターゲットのドキュメント数と検証・エイリアス付け替えの成否を含む `cutover_context` が報告されます。`_list` エンドポイントはクラスタ内のすべての移行を一覧化し、`_cancel` エンドポイントは終了状態にない移行を停止して後始末を行います。

## シャード数のスケーリング

マッピングやドキュメント形状の変更は、ほぼ上で示した transform の話です。シャード数の変更には、試す前に知っておく価値のある機微が 1 つあります。

AOSC はコピーとリプレイの過程で各ドキュメントのルーティングを保持するため、ドキュメントは正しいターゲットシャードに着地します。厄介なのは削除です。OpenSearch のオペレーション履歴は、削除されたドキュメントの `_id` は記録しますが、そのルーティングキーは記録しません ([OpenSearch issue 20907](https://github.com/opensearch-project/OpenSearch/issues/20907))。そのためターゲットのシャード数が異なると、リプレイされた削除が対象のドキュメントを取りこぼす可能性があります。

AOSC は、シャード数を維持する場合や、2 のべき乗倍に増やす場合といった、よくあるケースを扱えます。これは shard split のロジックが決定的であり、あるオペレーションについてソースシャードからターゲットシャードを算出できるためです。それ以外の変更、たとえば縮小や 2 のべき乗でない倍率での拡大は、カスタムルーティングを使っている場合にドキュメントが残ってしまう可能性があるので、AOSC はユーザーがそのリスクを明示的に受け入れないかぎり実行しません。

![2 のべき乗分割時のシャード対応図](/images/online-index-migration-and-shard-scaling-in/99acedf6ec8d.png)
*2 のべき乗分割で削除が正しく反映される理由。各ソースシャードは固定的なターゲットシャードのブロックに対応するため、ルーティング情報のない削除もそのブロック内にファンアウトできる。*

シャード数の変更を予定していて、とくにカスタムルーティングを使っている場合は、まず [Routing and Replay](https://atlassian-labs.github.io/opensearch-aosc/develop/concepts/routing-and-replay) を参照してください。どのレイアウトが安全でその理由は何かを、正確に説明しています。

## 運用上のセーフガード

うまくいかない状況で移行がどう振る舞うかは、いくつかの設計上の選択が形作っています。

- **Fail closed (失敗時はクローズ)。** エイリアス付け替えの前に移行が失敗した場合、エイリアスはソースに残ります。AOSC は、後始末が必要な中途半端な切り替えよりも、リトライ可能な失敗した移行のほうを選びます。
- **バックプレッシャー。** バックフィルはノードごとの permit、バッチサイジング (固定または適応)、繰り返しの書き込み失敗後のバックオフによってスロットリングされます。本番トラフィックも受け持っているクラスタを、移行が押しつぶさないようにします。
- **切り替え前の検証。** エイリアスが移動する前に、設定可能な許容範囲でドキュメント数を比較します。ドキュメントを黙って取りこぼした移行が成功として完了することはありません。
- **実行時の変換エラーは声を上げて失敗する。** 変換スクリプトは開始時にコンパイルされてドライランされますが、移行中に特定のドキュメントで例外が投げられた場合、誤ったデータを書くのではなく、そのワーカーが失敗します。

## AOSC が合わないケース

AOSC はすべての移行に向いているツールではありません。以下のケースでは使わないでください。

- **クロスクラスタ移行。** AOSC は同一クラスタ内のみが対象です。ただし将来的にクロスクラスタサポートが追加される可能性はあります。
- **エイリアスを使わない移行。** 具体的なインデックス名を直接読み書きしているアプリケーションは、切り替えに追随しません。エイリアスは省略可能ではありません。

## 試してみる

感覚をつかむ一番の近道は、ローカルで移行を実行してみることです。Your First Migration チュートリアルは、Docker クラスタを立ち上げ、連続書き込みを行うソースインデックスを作成し、マッピングとシャード数を変えたターゲットへ移行し、リトライされる書き込みも含めて切り替えの一部始終を数分で観察できるようにします。

AOSC は Apache 2.0 のもとで開かれた形で開発されています。Atlassian Labs のプロジェクトであり、メンテナンスとトリアージはベストエフォートで SLA はありません。育った環境の外でも役に立つツールになってほしいと考えており、フィードバック・Issue・コントリビューションを歓迎します。
