**TL;DR:** AOSC (Automatic Online Schema Change) プラグインを使うと、稼働中の OpenSearch インデックスを、マッピング、設定、シャード数の異なる別のインデックスへ、同じクラスタ内で移行できます。既存ドキュメントをバックフィルし、コピー中に到着した書き込みをリプレイし、短時間の書き込みブロックのあとにエイリアスを切り替えます。アプリケーション側で必要なのは単純なリトライ処理だけです。シャード数の変更は、同数のまま移すか 2 のべき乗倍に増やす場合であれば安全に行えます。それ以外のレイアウトには注意点があります。AOSC はオープンソース (Apache 2.0) で、Atlassian Labs が開発し、GitHub で公開しています。

OpenSearch を本番で長く運用していると、いずれ OpenSearch が動作中の変更を許さない項目に手を入れたくなる場面がやってきます。フィールドの型、アナライザ、ルーティングレイアウト、プライマリシャード数などです。1 年前に設計したマッピングがデータの実態と合わなくなっていたり、30 GB のうちは扱いやすかったシャードが 100 GB では扱いづらくなっていたり、といった状況です。

このとき定石になるのは、望みの形の新しいインデックスを作ってデータをコピーする方法です。ここまではよく知られています。難しいのは、コピーしている間に稼働中のインデックスで起きることをすべて捌ききる部分です。書き込みは絶え間なく到着しますし、削除も取りこぼすわけにはいきません。最後にはアプリケーションが、データを取りこぼさないまま新しいインデックスへ接続を切り替える必要があります。

本記事では、この一連の作業を扱うオープンソースの OpenSearch プラグイン、Automatic Online Schema Change (AOSC) を紹介します。AOSC は稼働中のインデックスを、あらかじめ用意しておいた移行先インデックスへ移行します。移行先のマッピング、設定、シャード数、ドキュメントの形は移行元と異なっていて構いません。移行中のほとんどの期間、移行元は書き込みを受け付け続けます。既存ドキュメントをバックフィルし、コピー中に発生した書き込みを取りこぼさないよう移行元の操作履歴をリプレイし、移行元に短時間の書き込みブロックをかけたうえでエイリアスを切り替えます。

AOSC は完全に無停止のツールではなく、あらゆる移行に向いているわけでもありません。本記事では AOSC が対象とする問題、動作の仕組み、シャード数を安全にスケールする方法、そして適用範囲の境界を順に説明します。自分のワークロードに合うかどうか判断するための材料にしてください。

## 稼働中のインデックスを既存のツールで作り直す

OpenSearch には、データを移動したりインデックスを作り直したりする手段がいくつか用意されています。それぞれ特定の状況では有効ですが、移行元のインデックスへの書き込みが止まらない状況では、どれも対応しきれない部分が残ります。

- **[`_reindex`](https://docs.opensearch.org/latest/im-plugin/reindex-data/)** は、移行元のある時点のスナップショットを新しいインデックスへコピーします。移行元を止められる場合や、コピー中に到着する書き込みを別経路で整合できる場合には無難な選択肢です。書き込みが多いインデックスでは、その整合こそが問題の中核ですが、`_reindex` は開始後に到着する書き込みを追跡もリプレイもしません。
- **[`_split`](https://docs.opensearch.org/latest/api-reference/index-apis/split/)** はシャード数を増やせますが、整数倍への拡張のみ、`read-only` にマークしたインデックスに対してのみ、かつインデックス作成時に十分な `routing shards` を設定していた場合に限られます。ドキュメントの作り直しやマッピングの変更はできません。
- **[`_shrink`](https://docs.opensearch.org/latest/api-reference/index-apis/shrink-index/)** は独自の前提条件のもとでシャード数を減らせますが、こちらもドキュメント自体には手を加えません。
- **手組みのパイプライン** (`_reindex` を実行し、そのあと変更を追随し、切り替える) を組めば完全に自由になりますが、バックフィル、書き込みリプレイ、検証、リトライ挙動、ロールバックを自分で設計するコストがかかります。そのいずれにも、微妙な正しさのバグを埋め込む余地があります。

これら OpenSearch 標準の機能に共通するのは、移行元への書き込みを止めることを前提にしているか、整合を取る仕組みをユーザー側で用意することを前提にしているか、そのどちらかだという点です。本番の書き込み経路の中核にあるインデックスでは、どちらも現実的ではありません。

![手組みの経路と AOSC の比較図](/images/online-index-migration-and-shard-scaling-in/28ea29a71049.png)
*手組みの経路 (左) では、コピー、二重書き込み、整合、切り替えのロジックをすべてのアプリケーション側に埋め込むことになります。AOSC (右) では、アプリケーションは 1 つのエイリアスを見続けたままで、移行処理はクラスタ側に閉じ込められます。*

## AOSC の役割

AOSC は「稼働中のインデックスをコピーして切り替える」一連の作業を 1 つのプラグインにまとめたものです。適用範囲は、正しく動作させられるケースに意図的に絞っています。

- 移行は単一クラスタ内で行う (移行元と移行先が同じ OpenSearch クラスタに存在する)。
- 移行先インデックスはすでに存在し、目的のマッピング、設定、シャード数で自分で作成しておく。
- アプリケーションは [エイリアス](https://docs.opensearch.org/latest/im-plugin/index-alias/) 越しに書き込むため、AOSC は切り替え時にそのエイリアスを移行元から移行先へ付け替えられる。
- アプリケーションは、切り替え中の短い時間帯に拒否された書き込みをリトライする。

これらの条件が揃っていれば、移行元インデックスに対する 1 回の API 呼び出しで移行を開始できます。あらかじめ作成しておいた移行先と、付け替え先のエイリアスを指定します。任意で [Painless スクリプト](https://docs.opensearch.org/latest/vector-search/vector-search-techniques/painless-functions/) を渡すと、移行の途中でドキュメントを変換できます。このスクリプトはバックフィルとリプレイの両方で実行されるので、移行中に書き込まれたドキュメントも、事前にコピーされたものと同じ形に変換されます。以下は不要になったフィールドを削除する例です。

```bash
curl -X POST 'http://localhost:9200/_plugins/_aosc/my-index-v1/_start' \
  -H 'Content-Type: application/json' \
  -d '{
    "target_index": "my-index-v2",
    "alias": "my-index",
    "transform_script": {
      "type": "inline",
      "source": "ctx._source.remove(\"legacy_field\")"
    }
  }'
```

あとは AOSC が移行を完了まで進めます。進捗はステータス API から随時確認できます。移行ごとのオプションで、切り替え前にシャードがどれだけ遅れていても許容するか、ドキュメント数をどのくらい厳密に検証するかを調整できます。

## 移行はどう進むか

AOSC はオーケストレーションとデータ移動を分けて動きます。コーディネーターは cluster-manager ノード上で動作し、移行をフェーズごとに進めます。シャードワーカーは移行元のプライマリシャードを保持するデータノード上で動作し、データのすぐそばで実際の読み書きを担当します。移行が実行中の間、現在のフェーズは cluster state に保持されます。移行そのものの履歴は `.aosc-migrations` システムインデックスに残ります。

![AOSC のアーキテクチャ図](/images/online-index-migration-and-shard-scaling-in/64f0ef8e53a7.png)
*オーケストレーションは cluster-manager ノードで動き、データ移動の処理はデータノード上でシャードのすぐそばで動きます。両者は cluster state (コーディネーターからワーカーへ) と transport action (ワーカーからコーディネーターへ) を通じて連携します。*

移行が正常に完了する場合は、以下のフェーズを通過します。

1. **Validate (検証)。** 移行元、移行先、エイリアスが存在して整合していること、プラグインがすべてのノードに同じバージョンでインストールされていること、ルーティング構成が AOSC の扱える形になっていること (詳細は後述) を確認します。AOSC は移行先を自動生成しません。目的の形に移行先を整えるのはユーザー側の役目です。
2. **Prepare the target (移行先の準備)。** レプリカを 0 に、refresh を無効にするなど、コピー向けの一時設定を適用してバックフィルを高速化します。これらの設定は切り替え前に元に戻します。
3. **Backfill (バックフィル)。** 各シャードワーカーが移行元の既存ドキュメントを読み込み、移行先へインデックスします。変換スクリプトが渡されていれば、その処理も同時に適用します。読み取りには retention lease を張るので、ワーカーが必要としている操作履歴が途中で消えることはありません。
4. **Replay (リプレイ)。** バックフィルのあと、ワーカーは移行元シャードの操作履歴を読み、コピー中に到着していた書き込みと削除を移行先へ適用します。これによって、書き込みを受け続けている移行元に、移行先が追随していきます。リプレイは、移行元のすべてのプライマリシャードで、移行先が切り替え可能なところまで追いつくまで続きます。遅いシャードや負荷の集中しているシャードがある場合は、切り替えを強行せずにこのフェーズで待機します。
5. **Cut over (切り替え)。** AOSC は移行元に書き込みブロックをかけ、ワーカーに最後の操作をリプレイさせます。移行元と移行先のドキュメント数が指定した許容範囲内で一致することを確認したうえで、エイリアスを移行元から移行先へ付け替えます。
6. **Complete (完了)。** エイリアスは移行先を指すようになります。デフォルトでは古い移行元に書き込みブロックが残るため、エイリアス移動後に古いインデックスへ気付かないうちに書き込みが入る事故を防げます。ブロックを自動で解除する挙動もオプトインで選べます。

![AOSC の移行フローチャート](/images/online-index-migration-and-shard-scaling-in/11e7e9af4b82.png)
*移行の全体像を 1 枚にまとめた図。シャード単位のバックフィルとリプレイは移行元を稼働させたまま進み、そのあとの短い書き込みブロック区間で最終リプレイ、件数チェック、エイリアス付け替えを行います。*

ドキュメントには、各フェーズがプラグインの返すステータスフィールドとどう対応するかを、アニメーションで順に追える解説が用意されています。初めて実行する前に、全体像を頭に入れておくのに役立ちます。

## 切り替えの時間帯

アプリケーションから見て実際に影響が出る中断は、この切り替えだけです。切り替えの間は、ワーカーが最後の操作をリプレイしてエイリアスが付け替わるまで、移行元への書き込みが拒否されます。この時間帯は意図的に設けています。トラフィックを移す前に、移行先が追いついていることを AOSC が確認するために必要な時間です。目標は、この時間を無くすことではなく、できるだけ短く保つことです。

この時間の長さは、インデックスサイズ、シャード数、書き込み負荷、検証コスト、cluster-manager の応答性によって変わります。一律の数値を当てにせず、自分のワークロードで実測してください。AOSC 自体はこの時間を短く保つ設計になっており、既知の制限のドキュメントに実運用で観測されている範囲が記載されています。ユーザー側で用意するのはリトライです。ブロックがかかっている間に拒否された書き込みをアプリケーションがリトライすることで、エンドユーザーからはこの中断が見えなくなります。

## 移行のモニタリング

移行はどれもステータスエンドポイントから確認できるので、進捗を推測する必要はありません。

```bash
curl -s 'http://localhost:9200/_plugins/_aosc/my-index-v1/_status' | jq '.phase'
```

レスポンスにはコーディネーターのフェーズと、バックフィルおよびリプレイのシャード単位の進捗が含まれます。切り替えが完了すると、移行元と移行先のドキュメント数、検証結果、エイリアス付け替えの成否をまとめた `cutover_context` も加わります。`_list` エンドポイントはクラスタ内のすべての移行を一覧化し、`_cancel` エンドポイントは終了していない移行を停止して後始末を行います。

## シャード数のスケーリング

マッピングやドキュメントの形の変更は、ほとんど上の変換スクリプトで対応できます。一方、シャード数の変更には、実行前に知っておくべき注意点が 1 つあります。

AOSC はコピーとリプレイの間、各ドキュメントのルーティング情報を保持したまま処理するので、ドキュメントは本来置かれるべき移行先シャードに配置されます。問題は削除です。OpenSearch の操作履歴は、削除されたドキュメントの `_id` は記録しますが、そのルーティングキーは記録しません ([OpenSearch issue 20907](https://github.com/opensearch-project/OpenSearch/issues/20907))。そのため、移行先のシャード数が移行元と異なると、リプレイされた削除が本来消すべきドキュメントを取り逃す可能性があります。

AOSC は、シャード数を維持するケースや 2 のべき乗倍に増やすケースといった、よくあるパターンには対応します。shard split のロジックが決定的で、移行元シャードの情報だけから対応する移行先シャードを算出できるためです。それ以外の変更、たとえばシャード数を減らす場合や 2 のべき乗でない倍率で増やす場合は、カスタムルーティングを使っているとドキュメントが取り残されるおそれがあり、AOSC はユーザーがそのリスクを明示的に受け入れないかぎり実行しません。

![2 のべき乗分割時のシャード対応図](/images/online-index-migration-and-shard-scaling-in/99acedf6ec8d.png)
*2 のべき乗分割で削除が正しく反映される仕組み。各移行元シャードは固定の移行先シャード群と対応しているため、ルーティング情報を持たない削除も、そのブロックに絞ってファンアウトできます。*

シャード数を変更する予定があり、とくにカスタムルーティングを使っている場合は、まず [Routing and Replay](https://atlassian-labs.github.io/opensearch-aosc/develop/concepts/routing-and-replay) を参照してください。どのレイアウトが安全か、なぜ安全なのかが詳しく説明されています。

## 運用上のセーフガード

移行がうまくいかない場面での振る舞いは、いくつかの設計判断で決まっています。

- **失敗時は移行元に留める (Fail closed)。** エイリアス付け替えの前に移行が失敗した場合、エイリアスは移行元に残ったままになります。あとから後始末が必要になる中途半端な切り替えより、リトライすればやり直せる失敗のほうを選ぶ設計です。
- **バックプレッシャー。** バックフィルは、ノードごとの permit、バッチサイジング (固定または適応)、書き込み失敗が続いたときのバックオフによってスロットリングされます。本番トラフィックも同時に受けているクラスタが、移行によって過負荷にならないようにするためです。
- **切り替え前の検証。** エイリアスを移動する前に、設定可能な許容範囲で移行元と移行先のドキュメント数を比較します。気付かないうちにドキュメントを取りこぼしていた移行が、そのまま成功として扱われることはありません。
- **実行中の変換エラーは黙って握りつぶさない。** 変換スクリプトは開始時にコンパイルとドライランを行いますが、移行中に特定のドキュメントで例外が発生した場合は、誤ったデータを書き込むのではなく、そのワーカーを失敗させます。

## AOSC が合わないケース

AOSC はあらゆる移行に向いているわけではありません。以下のケースには使わないでください。

- **クラスタをまたぐ移行。** AOSC は同一クラスタ内のみが対象です。ただし将来的にクラスタ間の移行がサポートされる可能性はあります。
- **エイリアスを使わない移行。** インデックス名を直接指定して読み書きしているアプリケーションは、切り替えに追随しません。エイリアスは必須です。

## 試してみる

感覚をつかむのに一番早いのは、ローカルで実際に移行を動かしてみることです。Your First Migration チュートリアルでは、Docker クラスタを立ち上げ、書き込みが継続的に走る移行元インデックスを作り、マッピングとシャード数を変えた移行先へ移行するところまでを体験できます。リトライされる書き込みを含めた切り替えの一部始終を、数分で観察できます。

AOSC は Apache 2.0 のもとで公開の場で開発しています。Atlassian Labs のプロジェクトのため、メンテナンスとトリアージはベストエフォートで SLA はありません。プロジェクトが生まれた環境を超えて広く役立つツールになってほしいと考えており、フィードバック、Issue、コントリビューションを歓迎します。
