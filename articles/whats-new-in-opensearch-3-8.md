OpenSearch 3.8 は、ベクトル性能の向上、より幅広いエージェント連携、分析ワークフローを簡素化する新しいツールによって、検索・AI・オブザーバビリティの機能を拡張します。エージェントを外部システムに接続する場合でも、AI で検索の関連性を高める場合でも、新しいクエリツールでログやメトリクスを調べる場合でも、本リリースは OpenSearch ユーザーにとって実用的な改善を届けます。OpenSearch 3.8 の新機能には以下が含まれます。

- Model Context Protocol（MCP）連携をより多くのエージェントタイプに拡張
- gRPC トランスポートによる低レイテンシな ML 予測のストリーミング
- ベクトルの取り込みを最大 4.16 倍高速化し、radial search のスループットを最大 2.1 倍向上
- より多くの大規模言語モデル（LLM）プロバイダーを利用した検索関連性評価のスケール
- ビジュアルな Piped Processing Language（PPL）ビルダー、SQL クエリ、オンボーディングキャンバスによるログ分析の効率化
- 新しい PPL コマンドによる時系列データの整形・ピボット・比較

最新版の OpenSearch は [ダウンロードページ](https://opensearch.org/downloads/)から入手できます。以下で新機能を詳しく紹介します。更新の全リストは [リリースノート](https://docs.opensearch.org/latest/version-history/)を参照してください。

## 検索の高度化

AI を活用した検索アプリケーションには、高速な取り込み、柔軟なエージェント構成、スケール可能な評価が求められます。OpenSearch 3.8 は、最大 4 倍高速なベクトル取り込み、すべてのエージェントタイプでの MCP サポート、そして任意のプロバイダーに拡張された LLM-as-a-Judge によって、この 3 つを実現します。

### Base64 エンコードでベクトル取り込みを最大 4 倍高速化

OpenSearch 3.8 は、`knn_vector` フィールド向けに Base64 エンコードによるベクトル取り込みを導入し、クライアント側とサーバー側の両方で JSON 配列のシリアライズにかかるオーバーヘッドを解消します。float ベクトルはリトルエンディアンのバイトエンコード（doc values のバイナリ出力形式と対称）を使い、byte および binary ベクトルは生バイトエンコードを使います。JSON 配列では約 16 KB を占める 768 次元の float ベクトルが、Base64 ではわずか 4 KB になり、ネットワークのペイロードを 74% 削減します。これにより一括取り込みのスループットが最大 4.16 倍になり、中央値のレイテンシは 83% 低下します。この機能はサポートするすべての k-NN エンジンで透過的に動作し、マッピングの変更は不要です。ベクトルフィールドの値を Base64 文字列として渡すだけで利用できます。

### recall を改善しつつ radial search を 2 倍高速化

OpenSearch 3.8 は、radial search 向けにグラフ探索を再設計しました。コストの高いクエリではグラフ探索に上限を設けることで、これまで radial ワークロードで見られた大きなレイテンシのばらつきを解消します。1,000 万ベクトルのデータセット（768 次元、内積）でのベンチマークでは、radial クエリのスループットは OpenSearch 3.7 と比べて最大 2.1 倍になり、中央値のレイテンシは 45%、p90 レイテンシは最大 77% 低下しました。同時に平均の再現率（recall）は 0.85 から 0.97 へと 14% 向上しています。この改善は追加設定なしで有効になり、マッピング・クエリ・設定の変更は不要です。Lucene エンジンを使う既存の `min_score` および `max_distance` の radial クエリは、アップグレード後に自動的に恩恵を受けます。

### MCP 連携をエージェントタイプ全体に拡張

OpenSearch 3.8 は、MCP サポートを flow エージェントと conversational flow エージェントにも拡張し、より多くのエージェント構成が MCP 準拠の外部ツールサーバーに接続できるようにします。これまでは conversational エージェントと plan-execute-reflect エージェントだけが MCP 連携をサポートしていました。今後は 4 種類すべてのエージェントが、一貫したコネクタ設定で MCP システムにアクセスできます。ユースケースに最も合ったワークフローを設計しながら、組織のツール群を最大限に活用できます。

### 外部 MCP ツールの探索とカスタマイズ

外部 MCP サーバーのツールを扱う作業を効率化する 2 つの機能が加わりました。新しい list tools API（`GET /_plugins/_ml/connectors/{mcp_connector_id}/tools`）を使うと、接続済みの MCP サーバー上で利用できるすべてのツールを、名前・種類・説明・入力スキーマとともにプログラムから取得できます。エージェントを設定する前に外部サーバーを手作業で調べる必要がなくなります。使うツールを特定したら、コネクタ単位のツール説明のオーバーライドによって、LLM が各ツールをどう認識するかをカスタマイズできます。コネクタ設定に `tool_descriptions` マッピングを追加すると、外部サーバーを変更することなく、文脈に応じた説明を与えてツール選択の精度を高められます。本リリースの MCP まわりの改善に貢献してくれた ML Commons メンテナー、NetApp Instaclustr の Abdul Muneer Kolarkunnu 氏に感謝します。

### エージェントメモリの保持ポリシーでストレージ増加を制御

エージェントメモリのコンテナが、保持ポリシーを設定できるようになりました。期限切れのセッション、長期メモリ、履歴エントリを、時間または件数の上限に基づいて自動的に削除するため、手動のクリーンアップスクリプトが不要になります。運用者はクラスタ全体のデフォルトを設定してフリート単位で管理することも、コンテナごとにポリシーを設定することもできます。重要なメモリはピン留めして削除対象から除外できます。この実験的機能は 24 時間周期で適用され、メモリの際限ない増加をなくして予測可能なストレージ制御を実現します。

### gRPC トランスポートで ML 予測を高速にストリーミング

ML Commons のストリーミング推論が、トランスポートとして gRPC をサポートするようになりました。これまでストリーミング予測とエージェント実行は、HTTP と Server-Sent Events を使った REST 経由でのみ利用でき、チャンクごとにテキストベースのエンコードのオーバーヘッドがありました。新しい `PredictModelStream` と `ExecuteAgentStream` のメソッドを使うと、OpenAI Chat Completions や Amazon Bedrock Converse のような外部ホストのモデルから、HTTP/2 上のプロトコルバッファを使って 1 トークンずつレスポンスをストリーミングできます。このバイナリトランスポートは、同等の REST ストリーミング API と比べてレイテンシと CPU オーバーヘッドを抑え、レイテンシに敏感なアプリケーションや高スループットなアプリケーションに役立ちます。

### 新しい LLM プロバイダーで LLM による評価を生成

Search Relevance Workbench の LLM-as-a-Judge は、OpenAI に限定されなくなりました。プロバイダー固有のコネクタブループリントを設定することで、任意の ML Commons コネクタを通じて関連性の自動判定を生成できます。OpenAI、Azure OpenAI、DeepSeek、Ollama（およびその他のローカルの OpenAI 互換サーバー）、Google Gemini、Amazon Bedrock 上の Anthropic Claude、Amazon Bedrock Converse API 向けに、すぐに使えるブループリントが同梱されています。本リリースではさらに、タイムアウトやレート制限エラーといった一時的なプロバイダー障害が明確に報告されるようになりました。新しいメタデータのサマリーには、クエリの総数・成功数・失敗数が表示され、Dashboards の判定ビューにはドキュメントごとのステータス列が表示されるため、欠落した評価がひと目で分かります。

### Mustache テンプレートで検索実験をパラメータ化

Search Relevance Workbench が、検索設定で Mustache のテンプレート変数をサポートするようになりました。フィルタの組み合わせごとに設定を複製することなく、複数パラメータの実験を組み立てられます。これまで検索設定は単一値の `%SearchText%` プレースホルダーしか受け付けず、実験は単純なキーワードクエリに限られていました。今後は `{{queryText}}` に加えて、クエリセットのエントリで定義した任意のカスタムフィールド（カテゴリ、ブランド、ステータスのフィルタなど）を、クエリ DSL 内で直接参照できます。従来の `%SearchText%` の記法もそのまま動作し、システムが使用中の形式を自動判別します。

## オブザーバビリティと分析

ユーザーは、ツールを切り替えたりクエリを一から書いたりせずに、オブザーバビリティのデータから実用的な知見へ最短で到達したいと考えています。OpenSearch 3.8 は、ビジュアルな PPL ビルダー、エディタ内での lint、Discover logs での SQL サポート、メトリクス探索からのワンクリックのアラート作成によって、このワークフローを効率化します。

### Explore logs の強化でログ分析の知見に素早く到達

OpenSearch 3.8 は、あらゆるスキルレベルの運用者や開発者に向けて、ログ分析のワークフローを効率化する Explore logs の強化を導入します。新しいビジュアルな PPL クエリビルダーを使うと、構文を手で書く代わりに、メニューからフィルタ・集計・並べ替えの条件を選んでクエリを構築できます。完全に制御したいときは、ビジュアルビルダーと生のコードエディタをシームレスに切り替えられます。SQL を使いたい場合は、Discover logs が SQL クエリの実験的サポートを備えました。日付ピッカーと完全に統合され、Logs・Visualization・Statistics の各タブで利用できます。

新しい Explore logs のオンボーディングキャンバスは、クエリを 1 つも書く前にデータを把握するのに役立ちます。キャンバスにはインデックスごとのカードが表示され、重大度のヒストグラムとライブのログ行プレビューをひと目で確認できます。さらに、生のインデックスを永続的で再利用可能なデータセットに変える手順を案内し、データがクラスタに到着してから実際の調査に着手するまでの時間を短縮します。これらの更新はオプトインで利用でき、OpenSearch のオブザーバビリティツールを初めて使うユーザーに簡素化された体験を提供します。更新後のインターフェイスを以下に示します。

### 新しい PPL コマンドでデータを整形・比較

OpenSearch 3.8 は、PPL の Calcite 実装に 4 つの新しいコマンドを追加します。これらのコマンドを使うと、クエリ結果の整形、期間の比較、分析や可視化に向けたデータの準備が容易になります。

- 新しい `makeresults` コマンドは、インデックスからデータを読み込まずにメモリ上で行を生成します。タイムスタンプ付きの固定数の行を生成することも、インラインの型付きテーブルを生成することもでき、クエリのテスト、eval 式の構築、ドキュメント例の作成に便利です。
- `foreach` コマンドは、同じ eval 式を複数のフィールドや配列要素に適用します。フィールドごとに式を繰り返し書く必要がなくなります。
- `xyseries` コマンドは、グループ化された行指向の結果を、系列ごとに 1 列を持つ横長のテーブルにピボットします。出力がダッシュボードやチャートに適した形になります。
- `timewrap` コマンドは、timechart の出力を、日次比較や週次比較といった期間同士の比較用に整形します。各期間を別々の列に配置します。

### 実行前に PPL クエリの誤りを検出

OpenSearch 3.8 は、エディタで入力しながらクエリを検証する PPL の lint エンジンを導入します。このエンジンは、事前の並べ替えを伴わない非決定的な `head`、暗黙のうちに null を返すゼロ除算の式、サポートされていないウィンドウ関数や無効化された結合タイプといったよくある落とし穴を検出し、構造化された説明とともに実用的な診断を提供します。フィールドを認識した検証は、不明なフィールド参照を特定し、近い候補があればワンクリックで置き換えを提案します。コマンドのタイプミス検出は、綴りを間違えたコマンドを「もしかして」という明確な提案に変え、インラインのクイックフィックスを添えます。この機能はオプトインで、各ルールは Advanced Settings で個別に有効化・無効化・重大度の調整ができます。

### OpenSearch を離れずに Grok パターンをテスト

Dev Tools の新しい Grok Debugger を使うと、外部ツールを使わずに OpenSearch Dashboards 上で直接 Grok パターンを構築・検証できます。サンプルのログ行を貼り付け、Grok パターンを書き、抽出をシミュレートすれば、解析されたフィールドをすぐに確認できます。カスタムパターンを定義することもできます。設定を開発・テストする場所でパターンの試行を完結できるため、取り込みパイプラインの開発が効率化されます。

### メトリクス探索から直接アラートルールを作成

これまで、メトリクスのパターンを見つけてアラートに変えるには、複数のページを行き来する必要がありました。OpenSearch 3.7 で導入されたネイティブの Prometheus 連携を土台に、3.8 ではこの機能を拡張します。Discover Metrics ページを離れずに、メトリクスのパターンを特定してそのままアラートを作成できるようになりました。ツールバーの新しい Create alert rule アクション（PromQL を使って Prometheus データソースを問い合わせているときに利用可能）でルールを定義できます。PromQL 式を入力し、しきい値・比較演算子・評価間隔・任意のラベルやアノテーションを設定します。設定を保存すると、ルールは指定した Prometheus データソースに作成され、すぐに Alerting Rules タブに表示されます。別のワークフローでルールを手作業で作り直す必要はありません。

OpenSearch Project は、プラットフォームサポートとインフラに関する以下の更新をお知らせします。

### OpenSearch における Amazon Linux 2 サポートの非推奨化

OpenSearch は、将来のバージョンで、継続的インテグレーションのビルドイメージおよびサポート対象 OS としての Amazon Linux 2 を非推奨にする予定です。Amazon Linux 2 は 2026 年 6 月 30 日にサポートを終了しました。詳しくは [AWS の FAQ ドキュメント](https://aws.amazon.com/jp/amazon-linux-2/faqs/)を参照してください。互換性のある OS の一覧は [サポート対象 OS](https://docs.opensearch.org/latest/install-and-configure/os-comp/)を参照してください。
